# Access Management Service

Backend-сервис управления выдачей доступа сотрудников к внутренним ресурсам
компании: сотрудник создаёт запрос, запрос проходит согласование, после чего
доступ выдаётся асинхронно через внешнюю систему.

## Запуск

```bash
cp .env.example .env      # необязательно: без .env возьмутся значения из .env.example
docker compose up --build
```

Поднимаются три контейнера: `api`, `worker`, `db` (PostgreSQL 16). Миграции
применяются автоматически при старте `api`, демонстрационные пользователи и
ресурсы засеваются идемпотентно. API доступен на `http://localhost:8000`,
Swagger — на `/docs`.

Postgres проброшен на хост как **5433** (5432 часто занят другим проектом).

### Демонстрационные данные

| Токен | Пользователь | Роль |
|---|---|---|
| `token-alice` | alice | employee |
| `token-bob` | bob | employee |
| `token-sec` | security-user | security |

| Ресурс | Владелец | Критичность |
|---|---|---|
| `gitlab` (id 1) | bob | normal |
| `analytics-dashboard` (id 2) | alice | normal |
| `production-database` (id 3) | bob | high |
| `broken-service` (id 4) | bob | normal — провайдер всегда отказывает |

Токены и ресурсы задаются переменными `SEED_USERS` и `SEED_RESOURCES`; это
заведомо публичные демонстрационные значения, а не секреты.

### Сквозной сценарий

```bash
# alice запрашивает доступ к gitlab
curl -X POST localhost:8000/api/v1/access-requests \
  -H "Authorization: Bearer token-alice" -H "Content-Type: application/json" \
  -d '{"resource_id": 1, "reason": "нужен доступ к репозиториям"}'

# bob — владелец gitlab — одобряет
curl -X POST localhost:8000/api/v1/access-requests/1/approve \
  -H "Authorization: Bearer token-bob"

# через пару секунд воркер выдал доступ
curl localhost:8000/api/v1/access-requests/1 -H "Authorization: Bearer token-alice"
```

Отказ провайдера воспроизводится тем же сценарием на ресурсе `broken-service`
(id 4): после трёх попыток запрос переходит в `PROVISIONING_FAILED` с
заполненным `provisioning_error`.

## Тесты

```bash
docker compose up -d db
python3.12 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
docker compose exec -T db psql -U postgres -c 'CREATE DATABASE access_test'
```

Тесты работают с настоящим PostgreSQL — инварианты здесь держатся частичными
уникальными индексами и блокировками строк, и проверять их на заглушке
бессмысленно. Тестовая база берётся из `TEST_DATABASE_URL`; conftest
отказывается работать с базой, имя которой не оканчивается на `_test`.

## Архитектура

```
        HTTP                                  ┌────────────┐
  ───────────────►  api (FastAPI)  ──────────►│            │
                          │                   │ PostgreSQL │
                          │ одна транзакция:  │            │
                          │ статус + задача   │            │
                          ▼                   │            │
                    provisioning_jobs ───────►│            │
                                              │            │
                    worker  ─── FOR UPDATE ───┤            │
                       │        SKIP LOCKED   └────────────┘
                       ▼
              внешняя система (mock)
```

Код разложен по слоям, зависимости направлены внутрь — домен не знает ни про
SQLAlchemy, ни про HTTP.

```
app/
  domain/           сущности, правила переходов, доменные ошибки
  application/      сценарии (use cases) и порты к внешнему миру
  infrastructure/   PostgreSQL, репозитории, воркер, заглушка провайдера
  api/              FastAPI: роутеры, DTO, аутентификация, коды ответов
```

- `domain/entities.py` — корень агрегата `AccessRequest`: только его методы
  меняют состояние запроса, и только там живут правила «кто и что может».
- `application/` — сценарии складывают домен и порты, ничего не зная о том, что
  за ними Postgres.
- `infrastructure/db/repositories.py` — единственное место, где есть SQL,
  блокировки строк и `SKIP LOCKED`.
- `infrastructure/db/models.py` — таблицы; инварианты живут в БД, а не в коде.

### Модель состояний access request

```
                    ┌───────────────────────────┐
   POST /requests → │ PENDING_OWNER_APPROVAL    │
                    └───┬───────────────────┬───┘
         owner approve  │                   │ owner reject
                        │                   └──→ REJECTED (терминальный)
                        ▼
        ┌───────────────────────────────────────┐
        │ PROVISIONING   (задача в outbox)      │
        └────┬───────────────────────────┬──────┘
             │ выдача успешна            │ попытки исчерпаны
             ▼                           ▼
          ACTIVE (терминальный)   PROVISIONING_FAILED (терминальный)
```

Переход, не показанный на схеме, возвращает `409 invalid_transition`.
`PROVISIONING_FAILED` терминален: повторная попытка — это новый запрос.

## Основные архитектурные решения

**Почему нет брокера.** Задача выдачи кладётся в таблицу `provisioning_jobs` в
той же транзакции, что и перевод запроса в `PROVISIONING`. Это исключает
классическое окно потери: при отправке в брокер после `COMMIT` падение процесса
между этими двумя действиями оставило бы запрос навсегда висеть в
`PROVISIONING`. У задачи один потребитель, десятки задач в сутки, порядок и
фан-аут не нужны — брокер добавил бы инфраструктуру, не добавив гарантий.

**Как это масштабируется до брокера.** Если появятся несколько потребителей или
потребуется мгновенный пуш вместо опроса, таблица остаётся источником истины, а
рядом встаёт relay: читает `provisioning_jobs` и публикует в NATS JetStream,
воркер становится durable consumer с ack и redelivery. Гарантии те же, меняется
только транспорт. Вариант «только брокер, без таблицы» не подходит по причине
из предыдущего абзаца.

**Согласующий определяется сервером.** Клиент не передаёт, в каком качестве он
одобряет: права проверяются по владельцу ресурса на стороне сервера.

**Инварианты в БД.** Частичный уникальный индекс `uq_access_request_occupying`
не даёт завести второй незавершённый запрос или дубль активного доступа на пару
сотрудник+ресурс. Уникальный `provisioning_jobs.request_id` физически исключает
две задачи на один запрос. Проверка на стороне Python была бы TOCTOU.

**Блокировки.** Любое изменение статуса — и из HTTP, и из воркера — идёт через
`SELECT ... FOR UPDATE` на строке запроса, поэтому конкурентные решения
сериализуются. Воркер берёт блокировки в порядке «сначала задача, затем
запрос»; обратный порядок дал бы дедлок с HTTP-слоем.

## Надёжность: сценарии и решения

| Сценарий | Что происходит |
|---|---|
| Два approve почти одновременно | Строка под `FOR UPDATE`; один получает 200, второй — 409. Задача создаётся ровно одна |
| Повторный approve обработанного запроса | Запрещён моделью состояний → 409, второй выдачи не происходит |
| Approve и reject одновременно | Сериализуются той же блокировкой; побеждает один, состояние согласовано |
| Задача запущена повторно | Провайдер идемпотентен по паре (user, resource) — `ON CONFLICT DO NOTHING`; доступ не выдаётся дважды |
| Provisioning завершился ошибкой | `attempts++`, задача возвращается в очередь; после 3 попыток — `PROVISIONING_FAILED` с сохранённой причиной |
| Сервис перезапустился | Задача живёт в БД, а не в памяти. Захват удерживается lease-таймаутом (`locked_until`), протухший lease подхватывается заново |
| Несколько воркеров | `FOR UPDATE SKIP LOCKED` — воркеры не ждут друг друга и не берут одну задачу дважды |

## Security

- Аутентификация — `Authorization: Bearer <token>`; в БД хранится только
  `sha256(token)`.
- Личность и роль вычисляются **только** на сервере. Ни один эндпоинт не
  принимает `user_id`, `role` или `owner_id` из тела, query или заголовков —
  объявить себя владельцем ресурса или security-пользователем нельзя.
- Владелец определяется как `resources.owner_id == current_user.id`; заявитель
  не может согласовать собственный запрос, даже если владеет ресурсом.
- Чужой запрос на чтение отдаётся как `404`, а не `403`: перебором id нельзя
  узнать о существовании чужих запросов.
- Секретов в коде нет; конфигурация — через переменные окружения. Образ
  собирается с `.dockerignore`, `.env` и `.git` в него не попадают.
- Параметры запросов не пишутся в логи (`hide_parameters=True`), тексты ошибок
  не отражают пользовательский ввод.

Известные ограничения перечислены в [ASSUMPTIONS.md](ASSUMPTIONS.md).

## Observability

- `GET /health` — liveness, `GET /ready` — readiness с проверкой БД.
- Логи структурированные (JSON), с уровнями; воркер логирует каждую попытку
  выдачи, её результат и окончательный отказ.
- Состояние выдачи видно через API: поле `provisioning` содержит число попыток
  и последнюю ошибку.

## CI/CD

`.github/workflows/ci.yml` на каждый push и pull request: `ruff check` и
`ruff format --check`, применение миграций, весь набор тестов против настоящего
PostgreSQL, сборка Docker-образа.

**Что было бы после успешного build в production.** Образ с тегом коммита
публикуется в registry. Миграции применяются отдельным job'ом до выката — они
обратно совместимы, поэтому старая и новая версии какое-то время работают на
одной схеме. Дальше rolling deploy `api` с проверкой `/ready` перед переводом
трафика, затем перезапуск воркеров (они безопасно переживают остановку:
незавершённая задача вернётся в очередь по истечении lease). Откат — выкат
предыдущего тега образа; миграции откатывать не требуется.

## Структура API

```
POST   /api/v1/access-requests           создать запрос
GET    /api/v1/access-requests           список (фильтры: status, resource_id)
GET    /api/v1/access-requests/{id}      запрос и состояние выдачи
POST   /api/v1/access-requests/{id}/approve
POST   /api/v1/access-requests/{id}/reject
GET    /api/v1/resources                 список ресурсов
GET    /health, GET /ready
```

Ошибки возвращаются единым форматом:

```json
{"error": {"code": "invalid_transition", "message": "..."}}
```

Коды: `400`, `401`, `403`, `404`, `409`, `422`.
